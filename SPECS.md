# Тестовое задание для Junior+ Ruby on Rails разработчика

## 1. Описание задачи

Необходимо разработать API модуля трекера задач.

### Предметная область

Разрабатывается медицинская информационная система (МИС), включающая несколько модулей. Один из них - трекер рабочих задач для персонала.

Через этот модуль врачи и администраторы могут ставить себе рабочие задачи:

- провести операцию;
- связаться с клиентом;
- сделать обход пациентов;
- подготовить отчет;
- выполнить другие рабочие действия.

## 1.1 Что нужно сделать?

### Шаг 1. Реализовать базовый CRUD задач

Необходимо самостоятельно инициализировать приложение на Ruby on Rails API и реализовать базовые возможности трекера задач:

- создание задач;
- редактирование задач;
- удаление задач;
- просмотр задачи по ID;
- получение списка задач;
- фильтрация списка задач по дате;
- фильтрация списка задач по статусам.

Задача должна иметь как минимум:

- название;
- описание;
- дату выполнения;
- статус.

### Шаг 2. Добавить теги для задач

Необходимо реализовать возможность добавлять и удалять теги для задач.

Связь между задачами и тегами:

- у одной задачи может быть много тегов;
- один тег может быть добавлен множеству задач.

В системе обязательно должны присутствовать теги:

- `отчетность`;
- `операции`;
- `звонок`.

Удаление и изменение этих тегов должно быть запрещено.

### Шаг 3. Добавить настройки периодичности

Многие задачи для персонала являются периодическими.

Примеры:

- ежедневный обзвон пациентов;
- формирование отчетности по четным дням;
- еженедельные инвентаризации;
- задачи на конкретные календарные даты.

Необходимо дать пользователю возможность определять периодичность задачи и сделать так, чтобы задачи в трекере создавались или отображались с учетом этих настроек.

### Типы периодичности

Нужно поддержать следующие типы задач по периодичности:

- ежедневные - каждый `n`-й день;
- ежемесячные - на каждое определенное число месяца от 1 до 31;
- на конкретные даты - задачи создаются только на указанные даты;
- четные или нечетные дни месяца - задачи планируются только на четные или только на нечетные числа.

## 1.2 Реализация логики повторяемости задач

Способ реализации логики повторяющихся задач можно выбрать самостоятельно.

При проверке решения особое внимание будет уделяться следующим моментам.

### Проблема бесконечности

Если пользователь создает задачу `ежедневный обход` без даты окончания, она будет повторяться бесконечно.

Создавать в базе данных миллионы записей на 100 лет вперед - плохая идея.

Нужно придумать способ:

- как хранить повторяющиеся задачи;
- как отдавать список задач для запрошенного временного окна.

### Состояние конкретного экземпляра

Врач может отметить задачу как выполненную за сегодня, но это не должно помечать выполненными вчерашние или завтрашние повторения.

У каждого экземпляра периодической задачи в определенный день должно быть свое независимое состояние, например `status`.

### Исключения из правил

Бонусная опциональная задача.

Нужно подумать, как можно реализовать отрыв одного экземпляра от общего правила периодичности.

Например:

- врач перенес ежедневный обход только в эту среду на 2 часа позже;
- врач отменил повторяющуюся задачу только на сегодня.

## 1.4 Стек технологий

- Ruby: `3.4.x` или выше;
- PostgreSQL: `16+`.

Плюсом будет упаковка приложения в Docker / Docker Compose для быстрого запуска.

## 2. Результат

В качестве результата необходимо предоставить ссылку на репозиторий с выполненным тестовым заданием.

В репозитории обязательно должны присутствовать:

- инструкция по локальному запуску проекта;
- Swagger-документация;
- импорт чата с LLM в виде файла `HISTORY.md`.

## Комментарии к заданию

В задании намеренно не детализированы все требования до уровня пошагового технического задания.

Важно показать самостоятельное проектирование решения:

- какие сценарии учтены;
- какая структура базы данных выбрана для календарной логики;
- какие ограничения заложены;
- как обоснованы принятые решения.

Можно и нужно делать разумные предположения там, где требования не определены явно.

Такие предположения нужно коротко описать в `README.md`.

## Критерии оценки

При проверке будут обращать внимание на:

- качество и чистоту спроектированного API;
- глубину проработки бизнес-сценариев, связанных с задачами;
- работу с серией задач;
- работу с одиночной задачей;
- организацию кода;
- следование лучшим практикам Ruby on Rails.

## Использование LLM

Использование LLM и других инструментов разработки разрешено и поощряется.
